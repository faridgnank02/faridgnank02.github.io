Knowbase: a from-scratch RAG knowledge base

A year ago I would have reached for a managed vector database or an off-the-shelf RAG framework and called it a day. Instead I built Knowbase, a retrieval system written from scratch, one component at a time, over a real codebase. No retrieval frameworks, no embedding APIs, no magic. Every addition had to earn its place by moving the numbers — and it came out with a 0.90 MRR. Here is the story.

Why build from scratch

The honest reasons are learning, control, and evidence. Managed stacks are a black box: when retrieval is bad, you cannot easily say why, because the retrieval strategy is buried inside an opaque service. Building from scratch forces you to understand each moving part — vector search, full-text, fusion, reranking — and to measure what each one contributes. The discipline of a fixed eval set and a single metric table turns vague "it works" intuition into numbers you can defend.

The problem

Retrieval quality is the first problem. Dense vector search is great at semantic matches but blind to keywords; full-text search is the opposite. Either alone misses a large fraction of relevant documents. The second problem is freshness and sync: as the codebase changes, the vector index and the relational data can drift out of line, and you need a single source of truth you control.

The solution

Knowbase keeps everything in one Postgres 16 + pgvector table — dense vectors, full-text (BM25-lite), and a hybrid reciprocal-rank fusion of the two. Local embeddings (BAAI/bge-m3, 1024 dims, via sentence-transformers) mean no embedding API and no per-call cost. On top of the fused pool sits an LLM reranker that re-orders candidates. LLM steps go through a configurable gateway: Cerebras by default (gpt-oss-120b), OpenAI, any OpenAI-compatible endpoint, or Claude via the Anthropic SDK.

An ask pipeline ties it together: a planner routes each question to the right tool (search, exact-symbol grep_code, who_knows), re-attaches neighbor context, and synthesizes a cited answer. That gets reingested through distillation and a "bursting" pass so issues and code stay in sync.

The results

On a fixed 31-question eval over the 16,315-document corpus (recall@k and MRR), the numbers tell a clear story:

moderecall@1recall@3recall@10MRR
vector0.520.710.810.63
fts0.450.550.650.50
hybrid0.390.650.940.57
hybrid + rerank0.870.940.940.90

The pattern is the real insight: hybrid provides the recall pool, the reranker provides the ordering. Neither is sufficient alone — hybrid recall@1 is 0.39 and reranking without the fused pool would be starved of candidates. Only when combined do you get 0.90 MRR.

Three front ends

  • CLI (kb): search and ask from the terminal.
  • MCP server (kb-mcp): exposes raw, LLM-free tools (search, search_code, who_knows) over stdio so any agent can call the knowledge base.
  • Web UI (kb-web): a single-page app with search and ask modes.

Lessons

What I would do differently: measure before wiring in a reranker — it is the expensive component, and my data shows it only pays off once you have a good fused pool ready. I would also lock the eval set earlier and version it, since chasing a moving eval makes it hard to attribute an improvement. Finally, the sync between the generated document store and the live codebase is the maintenance cost I underestimated; I would automate the re-ingest trigger on merge rather than on-demand.

Knowbase ended up as a small, honest system that earns its claims. Full source and the measured post-by-post results are on GitHub.
